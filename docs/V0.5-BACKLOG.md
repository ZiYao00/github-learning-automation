> 状态：**仅记录，不执行。**
>
> 这份文档用于保存 v0.4 / v0.4.1 讨论中明确延后的能力。它不是 v0.5 的最终需求、排期或承诺；未来重新启动 v0.5 讨论时，应重新做需求优先级、架构冲突、安全边界与社区方案审查。

## 已形成的候选方向

v0.4 已经建立：

~~~text
GitHub
  ↓
Research Packet
  ↓
Capture Note
~~~

未来 v0.5 可以优先讨论如何消费这些长期资产，而不是重新开发另一套 GitHub Collector：

~~~text
Research Packet
  ├─ Deep Note
  ├─ Compare
  └─ Media Brief
       └─ Fresh Check（需要当前状态时）
~~~

这里的 Deep Note / Compare / Media Brief 仍只是候选 Derived Artifact，不代表已经决定实现。

## 初步分类，仅用于未来讨论

### 媒体与发布

- 完整视频生成
- Storyboard
- 图片 / 视频自动下载

这些能力若未来启动，应消费 Research Packet / Media Brief，并在对外发布前执行 Fresh Check；不应重新实现一套仓库采集器。

### 产品入口

- MCP Server
- Web UI

这两项属于访问与交互层，不应改变 Packet / Capture Note 的事实契约。

### 检索与知识基础设施

- SQLite
- Vector DB
- RAG
- BM25

v0.4.1 仍坚持文件系统 + JSON / Markdown 作为长期真源。未来即使引入索引或数据库，也应视为可重建的辅助层，而不是唯一事实库。

### Provenance / 标准化

- Claim-level line grounding
- 完整 OKF

当前 Evidence Map 只做到 Source → Section。若未来升级句子级 / 行号级证据，需要单独评估复杂度、稳定 ID、source version、stale detection 与迁移成本。

### GitHub 来源扩展

- Issues / PR / Discussions
- 私有仓库

这会改变当前“公开仓库、低权限、只读、固定 revision”的安全模型，未来必须单独设计授权、隐私、凭据与长期存储边界。

### 生命周期与增量刷新

- 自动清理 Snapshot
- 自动清理 runtime
- section-level incremental regeneration

当前策略仍是保留历史、避免 Agent 自动删除。未来若设计清理，应采用显式策略、预览与人工确认；增量刷新则需要建立稳定 section / evidence identity 后再讨论。

## v0.5 重新启动时的讨论顺序

建议未来按以下顺序重新评估：

1. 先确认最真实的新使用场景：Deep Note、Compare、Media Brief 哪个优先。
2. 验证 v0.4.x Research Packet 在真实收藏库中的长期表现。
3. 再决定是否需要 Fresh Check / section-level regeneration。
4. 只有检索规模真正成为瓶颈时，再讨论 BM25 / RAG / Vector DB / SQLite。
5. 媒体生成、MCP、Web UI、私有仓库等继续作为独立能力评估，不与基础收藏链路绑死。

## 当前冻结结论

在重新开启 v0.5 讨论前：

- 不实施上述 16 项能力；
- 不为它们提前增加 runtime dependency；
- 不改变 v0.4.x 的公开仓库安全边界；
- 不为了未来可能的数据库 / RAG 预先重构现有文件系统；
- 不把“可能放进 v0.5”理解为“v0.5 必须全部实现”。
